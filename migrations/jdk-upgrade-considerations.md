# JDK upgrades and JobRunr

Use this skill when upgrading from one JDK LTS to the next (17 → 21,
21 → 25) and you want to know what JobRunr cares about.

## What JobRunr depends on at the JDK level

- **Bytecode version of your job classes.** JobRunr analyses the call
  inside the lambda using ASM. The bundled ASM version must support the
  bytecode generated by your compiler. JobRunr keeps its ASM dependency
  current with recent JDKs; pin to a recent JobRunr release before you
  pin to a recent JDK.
- **`MethodHandles.Lookup` semantics** for lambda metafactory analysis.
  Stable across recent LTS.
- **Virtual threads** (JEP 444, JDK 21). JobRunr 7+ uses virtual threads
  for worker threads by default when running on JDK 21+.

## Virtual threads — what changes

From JobRunr 7+:

```properties
# Default on JDK 21+
jobrunr.background-job-server.thread-type=VirtualThreads
# Or force platform threads
jobrunr.background-job-server.thread-type=PlatformThreads
```

Default `worker-count` differs by thread type:

- PlatformThreads: `availableProcessors`
- VirtualThreads: `availableProcessors * 16`

The intuition: virtual threads cheaply block on I/O, so you want many
more in flight to absorb the wait time. JobRunr sets the default high
so that worker concurrency isn't the limiter — your DB pool or upstream
service usually is.

## Pinning — the JDK 21–23 gotcha

A virtual thread can't release its carrier while it holds a `synchronized`
lock. Legacy JDBC drivers, older logging frameworks, and older Spring
chains all trigger this. Symptom: jobs sit in `PROCESSING` indefinitely
with idle CPU and no exception.

Fix: upgrade to **JDK 24+** (synchronized no longer pins). Until then,
identify the hotspot with `jcmd <pid> Thread.dump_to_file` and grep for
`<carrying virtual thread> ... synchronized`; switch affected workers to
`PlatformThreads`.

## Recommendations

| Scenario | Suggested setting |
|---|---|
| JDK 17 | `PlatformThreads`, `worker-count` = `availableProcessors` |
| JDK 21, mostly I/O-bound jobs | `VirtualThreads` (default), watch for pinning |
| JDK 21, CPU-bound jobs | `PlatformThreads` |
| JDK 24+ | `VirtualThreads`, fewer pinning concerns |

## Common mistakes

- **Bumping JDK without bumping JobRunr.** ASM and lambda-metafactory
  details have evolved. Keep JobRunr on a release that explicitly tests
  your target JDK.
- **Assuming virtual threads help CPU-bound jobs.** They don't. Virtual
  threads are throughput for I/O-bound workloads. CPU-bound jobs still
  need real cores.
- **Setting `worker-count` low with virtual threads.** Defeats the
  purpose — the whole point is more in-flight work absorbing I/O waits.
